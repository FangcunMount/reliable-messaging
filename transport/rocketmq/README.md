# RocketMQ ordinary and transaction message adapters

The ordinary Publisher replaces transport behind the host-owned Outbox/Relay. The independent TransactionalSender prepares all half messages before one host UOW, then uses exact original-transaction witnesses and a bounded Checker. See the [transaction SDK contract](../../docs/02-接入指南/RocketMQ事务SDK.md) for SQL/GORM/Mongo/SQLAlchemy wiring, three-phase results and lifecycle ownership. Neither path changes consumer/business receipt semantics. Constructors perform no I/O, driver construction or goroutine startup. Publisher.Start and Subscriber.Subscribe are explicit network boundaries; Close drains actual work and reports deadline failures.

The pinned upstream client is github.com/apache/rocketmq-clients/golang/v5 v5.1.4. TLS verifies the system trust store by default; hosts may supply an explicit CA pool through Config.TLS. No insecure certificate verification is added. Credentials and route bindings are host-provided; deployment is maintained in the infra repository.

RouteBinding version1 uses rmq_t_ plus the first32 hex digits of SHA256(logicalTopic), and rmq_g_ plus the first32 hex digits of SHA256(logicalTopic NUL logicalSubscription). Bindings must be explicit and canonical. No route is learned from message metadata. Broker names never replace the logical topic used by protected-wire authentication, message identity or fingerprinting. The original body is sent unchanged.

V2 bindings additionally freeze NORMAL/TRANSACTION, owner and route revision; the shared logical subscription owns one in-flight budget across its physical inputs. Canonical encoding and cross-language vectors are defined in the transaction SDK contract.

For the ordinary Publisher, Confirmed requires an explicit nonempty send receipt. Timeouts, network errors and missing receipts remain Unknown. The configured server must independently prove synchronous flush and persistence; a confirmation does not prove consumer effect. Rejected covers local validation failures and explicit Broker validation/authentication/authorization refusal. Throttling and uncertain failures remain Unknown.

SimpleConsumer uses bounded receives, manual ACK, retry visibility and visibility renewal until the host deadline. For a fixed subscription, physical inputs are sorted before applying the existing round-robin cursor, so one empty input cannot be repeatedly selected because of Go map iteration order. This covers input selection within a group; it does not promise an end-to-end latency bound. Subscriber.Ready records recent successful receives per logical group, including empty polls, and does not prove progress for every physical input or business completion. A lost ACK reply does not settle the local delivery. After the delivery-attempt limit the host must durably record Failure before ACK; failed audit is retried. Broker native DLQ remains a monitored recovery obligation and is not a durable host business-failure record. Host handlers must respect cancellation; ignored cancellation remains active and can cause Close to time out.

Controlled driver tests alone do not prove real Broker behavior; infra also runs public SDK producers/consumers, exact wire/identity checks, packet commit faults and real process/Broker recovery. examples/rocketmq and python/examples/rocketmq_probe.py target explicitly provisioned disposable infra routes and verify actual send/receive evidence. They do not provision business queues or authorize recovery. Fixed-release evidence is indexed separately from production cutover and host business acceptance; cross-cloud throughput is outside M2.
