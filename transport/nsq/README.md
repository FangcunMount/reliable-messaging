# NSQ publisher lifecycle

For a new host integration, `NewManagedPublisher` takes an nsqd address, bounded driver configuration, optional logical-destination routes and an in-flight limit. The SDK constructs and pings the `go-nsq v1.1.0` Producer, owns it until `Close`, and returns an error when the broker cannot be reached. `Close(ctx)` stops new admission, waits for actual driver calls, then stops the producer. A timeout leaves ownership intact; a later `Close` may finish the drain and stop. If a host cannot wait for a stuck driver call, it may explicitly call `Interrupt()` after the graceful deadline, then call `Close` again to verify drain. An interrupted publication has an Unknown broker outcome. The host retains its Outbox transaction, original message identity, and decision on an Unknown result.

The older `New` constructor remains for hosts that deliberately lend an existing Producer. It neither connects nor starts goroutines, and `Drain` does not stop that borrowed Producer. Outbox messages use copied logical-destination routes; direct events can call `PublishRaw` with an explicit NSQ topic and already encoded bytes, without declaring routes. Both constructors use the same bounded sends and classification. Configure bounded driver dial/read/write timeouts.

`Publish` and `PublishRaw` return `Confirmed` only on a nil driver result. Missing/invalid local routes, invalid raw topics and empty raw bodies are `Rejected`; driver errors and context expiry are conservatively `Unknown`, because the broker may have received the message. For Unknown, the host retains the original application identity and wire bytes before any authorized retry. NSQ acceptance does not prove consumer handling or synchronous disk durability. The adapter does not retry internally.

The pinned driver's Publish call has no context parameter. Each admitted call runs with one bounded in-flight slot; context expiry returns Unknown but retains that slot until the actual call finishes. Repeated timeouts therefore cannot create unlimited background sends. The host should choose a limit aligned with Relay concurrency and account for possible duplicates while an earlier unknown send is still in flight.

Shutdown order with the borrowed `New` constructor:

1. Cancel Relay admission and wait for Relay.Run to return.
2. Call Publisher.Drain with a bounded context. Drain permanently stops new admission and waits for actual driver calls.
3. When drained, stop the host-owned producer, then close host databases.
4. If Drain times out, keep it visible as an incomplete shutdown. The host may call producer.Stop to interrupt remaining driver activity, then recheck Drain. A timeout is never successful drain evidence.

With `NewManagedPublisher`, stop Relay admission and wait for Relay.Run, then call `Close(ctx)` before closing host databases. Draining only Relay is insufficient to prove that the non-context-aware driver has stopped. Producer ownership is explicit for both constructors. Unit tests distinguish caller completion from driver completion; real integration checks an SDK-owned connection and closure, and separately drops the NSQ PUB response after broker acceptance to test Unknown plus byte-preserving duplicate delivery.

## Subscription binding candidate (M6-04B)

`NewSubscription` only validates a topic/channel, bounded attempt policy and injected handlers. It creates no connection, producer, consumer or goroutine. A host may wire it directly for low-level use, but the candidate `Subscriber` now manages two consumers per subscription with either explicit nsqd addresses or lookupd discovery: it connects the historical failure topic/channel to known source nodes **before** the business topic/channel. If the business topic is not yet registered, it selects one active nsqd from lookupd `/nodes` for failure-channel bootstrap. Both consumers then poll lookupd; a newly observed source is connected to the failure consumer before its terminal handoff. `DirectHandoff` borrows the failure consumer, creates source-nsqd producers during explicit delivery work, and drains/stops those producers on close. `NewSubscriber` itself starts no network work. Disposable tests cover a late nsqd kill/rejoin, lookupd outage followed by discovery of a newly joined node, and a real mid-handoff confirmation loss. IAM/QS service wiring and production recovery remain separate gates.

`Subscriber.Close(ctx)` stops new registrations before waiting for an in-progress NSQ connection. If its deadline expires during that connection, it returns the context error; the registration attempts cleanup when the bounded driver call finishes. The host must call `Close` again to verify all owned consumers and handoff sends have drained before closing databases. A deadline return alone is not a completed shutdown.

If registration fails after creating consumers, cleanup stops them and uses the registration context with a 35-second upper bound. When that cleanup cannot prove a complete drain, `Subscriber` retains the partial consumers and handoff under the same topic/channel identity. The host must call `Close` to finish and verify cleanup before discarding the subscriber or retrying the registration with a new instance. A failed `Subscribe` result alone is not proof that all started network work has stopped.

For a new durable business channel, the host can call `NewProvisioner` with a borrowed HTTP client and explicit nsqd HTTP URLs, then `EnsureChannel` before allowing the first publish. It creates the topic first and then the channel on every declared node. NSQ returns `TOPIC_NOT_FOUND` if `/channel/create` is called for an absent topic. A failed or partial preparation returns an error; the host must not treat that as readiness. The SDK does not infer an HTTP port from a TCP address or choose business topics. Re-run preparation when publishing nodes change. A disposable single-node NSQ test publishes before any business consumer starts and receives the original application ID and payload after Subscriber startup; multi-node changes still need fault testing.

`transport.Delivery` exposes application and physical identities separately. An explicit Ack/Nack takes precedence over a handler return; otherwise nil acknowledges and an error requeues. Once the budget is exhausted, the business handler is skipped and the original is only finished after a confirmed failure handoff. A lost handoff confirmation can create a duplicate failure record. The host's failed handler must durably record the handoff before returning nil; the SDK cannot infer that from a callback. Business idempotency and governance remain with the host. The focused isolated NSQ tests prove direct-address and lookupd registration/close, discovery after topic creation and lookupd recovery, late-node kill/rejoin between messages, two physical failure records after an accepted handoff with a real dropped confirmation, and real MySQL audit rejection/requeue/recovery. They do not prove the IAM/QS service audit adapter, broker fsync, service cutover or complete fault recovery.
