# reliable-messaging 文档维护约定

适用于现行设计、接入、包入口、发布索引和候选说明。历史材料保留原结论与范围，默认不执行现行正文的结构要求。阅读入口见[导航](README.md)。

## 什么是事实来源

| 要说明的事实 | 优先核对的来源 |
|---|---|
| 当前实现与前提 | 公开 API / 组合方式、源码、`go.mod`、`python/pyproject.toml`、SQL schema、机器样例 |
| 哪些行为经过验证 | 对应测试、实际日志和有来源的 CI 结果；同时写明隔离范围 |
| 什么版本可安装 | 指定 tag / commit 的 Release 与制品记录 |
| 宿主是否采用或验收 | 带采集时间的宿主部署、真实行为与业务验收材料 |

现行正文解释这些来源，不能覆盖它们。源码实现不能单独证明制品发布，tag 不能证明线上采用，健康容器不能证明业务验收。旧说明中的“尚未发布”也必须重新核对。

## 一处讲透，其他回链

通用身份、事务、状态、投递、恢复、安全由核心设计维护；语言特有的接线前提由接入指南维护。驱动包 README 保留安装、专有限制和索引，不再复制完整状态机。事件名、消费幂等、领域回执、权限时限、业务重试、指标阈值和部署单属于宿主文档。

设计正文先说明问题和结论，再解释职责、不变量、正常链路、失败窗口与取舍，最后链接源码与验证入口。复杂链路使用图或比较表。不要机械套每个小标题，也不要用接口目录或验收日志代替设计推理。

文首说明主题范围、适用语言/版本和关键限制；详细 SHA、Release 与 CI 放[发布索引](releases/README.md)或证据。状态使用“已实现”“待补证据”“规划改造”；表述当前 main 时说明它不是稳定版本保证。修改 API、wire、持久状态、事务、生命周期、安全或兼容条件时，在同一变更更新其唯一正文和必要 ADR。

## 链接与样例

- 仓库内使用相对链接，标题锚点遵循 GitHub Markdown。源码是参考来源；不要手抄全部签名或 schema 形成第二份权威契约。
- 跨仓库概览可链接仓库入口；声称特定代码行为时固定 commit，并说明核对日期。不得把个人绝对路径、浏览器会话、临时文件或生产密钥写入现行文档。
- 例子使用合成身份和专用资源。公开 API 例子必须能编译；事务例子复用真实隔离验证。代码片段标明省略的宿主函数，不伪装成完整可运行程序。
- 校验和不等同认证；技术重投不等同业务重试；`published`、FIN、业务持久回执必须指出确认对象。

## 归档和候选

旧文档迁移到[_archive](_archive/README.md)后，原入口保留短指引。保留失败、限制、采集日期和来源，不将旧“通过”重判为当前验收。迁移只调整必要的相对链接；归档清单保留迁移前后摘要。归档不是当前接入前置，不在其中持续追加现行合同。

已决定的长期取舍进入[ADR](04-设计决策/README.md)；未决定的变化进入 `proposals/`，写出待决问题、负责人职责和触发条件。每个 PR 不必产生一个 ADR。CI 大日志、生产正文和运行镜像不搬入 docs。

## 提交前检查

运行 `make docs-check`，需要 Python 3.11+，只使用标准库。它离线检查现行 Markdown 的相对链接、标题锚点、围栏和绝对本机链接；核对发布索引的 Python 源版本、兼容文档的 Go 最低版本以及归档摘要。检查器接受的 Markdown 范围见[检查器](../scripts/check_docs.py)，复杂 HTML / 动态渲染的正确性仍需人工查看。

运行 `make check` 和适用验证，入口见[测试与故障验证](03-维护与验证/测试与故障验证.md)。文档检查不联网推断 Release，不检查生产状态，不证明所有自然语言事实正确；作者需阅读源码，评审需复核责任和版本边界。
