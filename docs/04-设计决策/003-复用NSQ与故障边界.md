# ADR 003：复用NSQ与故障边界

状态：已采用。适用：当前NSQ 1.3.0 / Go go-nsq 1.1.0与Python可选pynsq 0.9.1合同。版本范围见[兼容与升级](../03-维护与验证/兼容与升级.md)。

## 问题与约束

IAM、QS已采用NSQ，核心需求是统一本地可靠意图、技术投递、消费接口与恢复合同。迁移Broker可改变拓扑、持久性和运维能力，但普通Publish不能与MySQL/Mongo事务原子提交。先迁移Broker不会消除双写窗口。

## 备选与选择

复用NSQ可保留现有topic/channel和运维能力，优先减少宿主重复实现。RabbitMQ等Broker具有不同的确认、路由和队列持久性配置，但还需消费者/拓扑迁移、逐流回退和同样的本地事务方案。Broker事务消息另需独立业务状态查询/回查设计，不能当成普通adapter替换。

当前选择复用NSQ，Go线不支持RabbitMQ。SDK通过transport接口隔离Broker；未来扩展以明确需求和实际故障证明立项，不先为未采用Broker增加空适配。

## 必须接受的故障边界

NSQ PUB OK表示当前Broker接受，不保证每次PUB同步落盘。固定隔离设置 `mem-queue-size=3000`、`sync-every=2500`、`sync-timeout=2s` 下，正常退出刷新后消息可恢复；SIGKILL之后仍可丢失已确认的内存消息。后者是已复现边界，不是崩溃恢复已通过。

因此标准Outbox的published并不保证必要效果最终存在，且不会因Broker丢失自动变回pending。宿主必须用权威业务事实/回执对账，并通过有审计的原行重排或回执型合同恢复，不能删除责任或生成新执行身份。

## 运输与运维责任

- 首次发送前需在声明节点准备durable业务channel；只建立topic不能保留未来channel所需的首消息。
- 终态运输预算耗尽后跳过业务handler；确认失败中转后才能FIN原消息。中转确认丢失可产生重复原身份，持久失败callback必须幂等。
- Go Subscriber可用lookupd；Python当前仅显式nsqd地址，不能外推动态发现能力。
- lookupd不可用时已连接节点仍可能继续投递，但新节点不能据此保证可发现。
- 节点故障、磁盘/主机丢失、复制、多节点容量和生产拓扑需独立证据；SDK不会安装Broker或修改共享生产参数。

复用NSQ接受运输持久性边界和宿主对账成本，不能用“至少一次”遮盖已确认消息内存丢失的具体窗口。

## 重新评估条件与证据

当实际业务要求更强的Broker落盘/复制保证、路由能力或可用性，且宿主回执/对账不能满足目标时重新比较Broker。评估需明确确认合同、失败窗口、迁移与回退水位，不能只比较产品功能表。
