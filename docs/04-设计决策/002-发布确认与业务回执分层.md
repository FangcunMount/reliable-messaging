# ADR 002：发布确认与业务回执分层

状态：已采用。适用：Go标准Outbox及Go/Python回执型adapter。本文解释为何两个合同共存；状态定义回链[事务与Outbox](../01-核心设计/事务与Outbox.md)，运输结算回链[投递与消费](../01-核心设计/投递与消费.md)。

## 问题与约束

Broker接受不证明消费者持久接单，NSQ FIN不证明最终业务效果。某些调用还存在“接收者已提交但回执丢失”的窗口，重发新的执行命令会破坏幂等或盲目重复未知模型调用。

已有Go标准Store终结于传输确认。Python最小原表adapter终结于宿主核实的持久接单callback。强行把所有 `Confirmed` 解释为同一事实，会改变既有合同。

## 备选与选择

| 方案 | 问题 |
| --- | --- |
| 所有成功都叫业务完成 | 混淆PUB、FIN、持久接单和最终效果，无法判断仍由谁恢复 |
| 将标准Store改成必须业务回执 | 破坏已有租约/结算语义，迫使所有消费者新增回执 |
| 仅保留PUB确认且删除宿主回执 | Broker丢失或回执丢失时无法安全对账必要效果 |
| 分开确认层次和独立状态 | 增加合同选择成本，但保持兼容并让责任可证明 |

采用独立合同：标准Store的 `Confirm` / `published` 记录传输确认；回执型Outbox区分 `staged`、`awaiting_receipt`、`confirmed`、`held`。`requires_receipt=true` 必须由宿主验证持久业务回执后结算；receipt-free final ACK按PUB确认结束，不建立ack-of-ack无限链。

Python原pending/delivered适配仍要求宿主callback核实原event_id持久接单，它不等价于Go leased Store或回执型schema。相同确认词必须始终附确认对象。

## 不变量与代价

- 接收handler返回之前，宿主必须提交其业务/Inbox/回执意图；SDK无法从普通nil返回自行证明数据库已提交。
- 未知PUB结果保留可能已接受的事实，技术重投不生成新身份或新密文。
- 迟到publisher/retrycallback不能撤销已确认或held状态。
- final ACK重排只恢复原回执通知，不授权再次业务执行；成功重发不消耗失败PUB预算，重复事件不撤销technical hold。

回执型合同需要持久回执路径、幂等接收者、正文保留和宿主业务对账。它也不能自动保证最终业务效果；任务已接单与模型已完成仍由宿主状态区分。

## 重新评估条件与证据

只有新的业务合同明确无需回执、或已提供等价的权威效果核验时才改变结算边界；需要按原未完成行迁移，不能统一改字段名称。
