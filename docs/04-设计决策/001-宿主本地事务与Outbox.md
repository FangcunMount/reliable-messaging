# ADR 001：宿主本地事务与Outbox

状态：已采用。适用：Go标准Store、Python原表适配及独立回执型adapter。详细合同见[事务与Outbox](../01-核心设计/事务与Outbox.md)。

## 问题与约束

业务事务提交后直接Publish存在退出/网络失败窗口；先发送再提交又可能让消费者看到随后回滚的事实。抽取SDK只能统一正确的机制，不能改变数据库与Broker不共享本地事务的事实。

IAM与QS有各自业务数据库，QS还有MySQL与Mongo。qs-ai依赖原任务和回执保护已接单、冻结配置与未知模型调用。SDK不能为了统一表而跨库移动这些权威事实。

## 备选与选择

| 方案 | 收益 | 代价或拒绝原因 |
| --- | --- | --- |
| 提交后直接Publish | 少表、低成本 | 提交后退出可能永久丢意图，不适合必达事实 |
| SDK中央数据库/消息服务 | 集中调度和维护 | 新的跨库双写窗口、独立部署/容量/权限，不能原子提交业务与意图 |
| XA/分布式事务 | 在适配范围内统一提交 | 跨存储/Broker约束与运维复杂度，并非现有宿主合同 |
| 原事务Transactional Outbox | 事实和意图同提交，进程恢复后可发现 | 延迟、重复投递、宿主迁移/幂等及本地持久记录成本 |

采用最后一项。SDK appender借用宿主已有事务，业务服务决定何时提交/回滚；提交后唤醒只是加速，周期扫描仍发现原持久意图。迁移、连接池、参数和部署由宿主负责。SDK不提供中央数据库、业务重试裁决或隐式建表。

## 不变量与代价

- 业务事实与意图同事务提交或回滚；绑定失败不得另开事务兜底。
- 技术恢复保留原producer、message_id、destination、指纹和字节。
- 构造/绑定不隐藏事务提交与schema迁移；明确自持有网络资源入口不改变业务资源所有权。
- 本地Outbox保证的是已提交意图可恢复，不是跨数据库原子性、端到端exactly-once或外部副作用必然完成。

每个宿主仍有持久表/集合和业务适配，属于有意保留的事务责任。应减少通用实现重复，不能以减少行数为由删除业务幂等或已接单事实。

## 重新评估条件与证据

只有新增Broker事务协议、可执行的状态查询/回查合同，或独立Relay确有容量/运维需求时才重新评估；必须重新说明本地事实与发送之间的失败窗口和未完成记录责任，不能把Broker替换等同于一致性解决。
