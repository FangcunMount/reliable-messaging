# 生命周期与恢复

可靠消息的停机目标是：停止接纳新工作后，已经接纳的工作仍能完成原结算；没有完成的部分保留可核对的原持久状态。取消 context、Relay.Run 返回、driver 停止和数据库关闭，是四件不同的事情。

SDK 没有独立进程管理器。宿主决定什么时候启动、怎样监督扫描错误、给停机留多少时间，并关闭自己的数据库和共享连接。本文解释每个对象实际持有什么，以及为什么必须按依赖关系退出；发布与消费确认见[投递与消费](投递与消费.md)。

## 谁持有资源，构造时是否已经启动

| 对象 | 构造与启动的真实行为 | 退出时谁负责 |
|---|---|---|
| Appender、Store、Relay.New | 绑定／校验；不迁移 schema，不开始扫描 | 宿主事务、连接池和 Run 监督 |
| NSQ `New` Publisher | 借用 Producer；不连接、不启动发送 | SDK Drain；宿主随后停止 Producer |
| `NewManagedPublisher` | 创建自己的 Producer，并实际连接、Ping | SDK Close 等真实发送后停止它 |
| NewSubscription | 无连接的消费结算绑定 | 宿主持有 driver consumer，停接纳后 WaitIdle |
| NewSubscriber | 只校验；Subscribe 才连接 | SDK 关闭自己创建的 consumers 和失败中转 producers |
| Redis adapter | 构造无网络；Watch 开自己的订阅 | Watch 关该订阅，宿主关共享 Redis client |
| Python PeriodicRelay | 构造不 create_task；await start 启动 | 宿主 stop/wait 和既有事件循环 |
| Python NSQSubscriber | start 开 readers/timers，借用 publisher map | 停自己的读者和任务，宿主停 Publisher／loop／数据库 |

“所有 SDK 构造器都没有 I/O”是不准确的。ManagedPublisher 明确承担连接所有权；它返回前已 Ping，构造失败会停止刚创建的 Producer。需要纯装配的宿主可以使用借用 Publisher，但必须自己设置有限的 dial/read/write 超时并保持借用对象存活。

这些对象不自动打开业务事务、提交事务或关闭借用池。部署成同一容器也不改变所有权：一个 goroutine 正在使用数据库时，另一个对象的 Close 成功不能授权提前关闭池。

## Go Relay 如何启动，扫描失败由谁看见

Relay.New 只验证 Store、Publisher、RetryPolicy、Observer 和时间边界。Run 才循环领取；同一个实例不能同时 Run 两次。

```go
// 片段：r 已通过 relay.New 构造；done 必须被宿主监督器读取。
runCtx, stopRelay := context.WithCancel(context.Background())
done := make(chan error, 1)
go func() { done <- r.Run(runCtx) }()

// 停机路径先停止业务入口，再停止新的扫描接纳。
stopRelay()
runErr := <-done
// 保存 runErr；完成下文的 Publisher 排空和资源关闭后再上报。
```

一批最多领取 Concurrency 条。每条已接纳投递有独立 PublishTimeout 和 WriteTimeout；Lease 必须大于两者之和，否则正常处理就可能被另一个发送者抢回。SDK 验证这些局部约束，却不能根据实际负载替宿主决定秒数。

ClaimDue 失败时，Run 发出 claim_failed 后返回错误。SDK 不在内部无限重启；宿主可以采用有上限的退避监督并降低 readiness。一次后续成功扫描，即使没有到期行，也会发 scan_succeeded，可用于恢复扫描健康。

Observe 同步执行，且多条发布可能并发调用它。它必须快速、不阻塞、并发安全；把缓慢邮件、远程指标写入或无界日志当 Observer，会拖住真实投递和停机。Err 是诊断对象，未经筛选不应原样作为公开日志。

## 取消时哪些工作还会继续

Run 每次接纳前检查取消。已经领取但尚未启动的行可能等待租约恢复；已经启动的投递用 `context.WithoutCancel` 保留当前结算机会，再分别附加发布和写入 deadline。

```text
1. 领取 E1，标为 publishing
2. 已接纳 E1 的 Publish
3. 宿主取消 Run
4. Run 不再启动下一条新工作
5. E1 尝试取得 PUB 结果，并写 Confirm／Retry／Quarantine
6. 已接纳批次结束，Run 返回
7. 宿主仍须等 Publisher 的真实 driver 调用排空
```

这里等待的是 SDK 调用合同，不是“无论什么回调都保证在某秒内结束”。Go 无法强行终止不遵守 context 的 Store、RetryPolicy 或 Observer。Publish 对调用者按时返回，也可能只是 Unknown，driver 在后台仍未结束。

持久租约提供崩溃后的恢复基础，不提供执行中止能力。A 的租约过期后 B 可领取；A 迟到的结算被 token/version 拒绝，但 A 的网络发布仍可能已经发生。原应用幂等仍必不可少。

## 为什么 Run 返回后还要 Drain Publisher

设 PublishTimeout=1 秒、真实 driver 调用耗时 3 秒。第 1 秒 Relay 得到 Unknown，写入重试决定后可以结束；第 3 秒 driver 仍可能成功完成 PUB。若第 1 秒就停 Producer 或关闭相关资源，宿主会失去对这次发送结果的观察。

借用 Publisher 的正确局部顺序：

```mermaid
flowchart LR
  Entry[停止业务新入口] --> Cancel[取消 Relay 接纳]
  Cancel --> Run[读取 Run 退出结果]
  Run --> Drain[Drain 等真实发送]
  Drain --> Producer[宿主停止借用 Producer]
  Producer --> Pool[宿主关闭依赖池]
```

Drain 永久关闭新的发布接纳；超时返回表示真实发送尚未全部结束，不是成功排空。超时后对象仍保留发送责任。宿主可以继续等待；需要强制中断时，显式停止自己持有的 Producer，再次 Drain 确认真实调用已退出。Drain 成功也不把先前 Unknown 改成 Confirmed：迟到 driver 结果释放 slot，不会重新结算已经返回的 Relay 调用。

ManagedPublisher.Close 执行相同排空，再停止自己持有的 Producer。Close 超时仍保留所有权，可再次调用。其 Interrupt 是显式强制路径：停止接纳并请求停止 driver，随后仍须 Close 验证。调用 Interrupt 不等于已经排空，也不能把在途 PUB 改记为 Confirmed。

已有 Unknown 或未结算的持久行继续按原事实恢复。不能在停机时“补一个成功状态”来让表看起来干净。

## Subscriber 注册失败与关闭超时怎样处理

Subscribe 先注册失败消费者，再连接业务消费者。注册过程中可能只建立了部分连接；取消注册或 Close 到期时，真实 driver 调用还可能继续结束。

例如 Subscribe 正在持锁连接，Close 在获取锁之前超时：此时已停止新注册接纳，却尚不能证明所有 Consumer.Stop 都已调用。宿主还须读取 Subscribe 的最终结果，再次 Close 核验。

Subscriber 保存部分注册留下的资源引用。宿主必须保留这个实例并再次 Close 核验，不能看到 Subscribe 返回错误就丢弃对象、同时创建第二份竞争订阅。

Close 的顺序是停止新注册、停止 business/failure consumers、等待各 StopChan、等待实际 Handler 空闲、最后关闭失败中转发送对象。返回成功才证明这些 owned 资源已结束；超时后实例仍处于停止接纳状态，后续 Close 继续承担清理责任。

Subscribe 的 ctx 控制注册过程，不等于业务投递的生命周期。后续 Handler 使用 SubscriberConfig.DeliveryContext；宿主若把启动期的短 context 当作整个服务 context，会使上线后投递持续取消。反之也不能认为注册 ctx 取消自动关闭了已成功建立的订阅。

## 同时消费、生产和扫描时怎样排列停机

“先关消费者还是先关 Publisher”没有脱离依赖的统一答案。如果消费者 Handler 还需要数据库写入业务回执、向同一个 Publisher 转交失败，先关闭这些依赖就会破坏其结算。

宿主应画出实际依赖，再执行：

1. 停止 HTTP/gRPC 新业务入口和新的后台业务接纳。
2. 停止订阅的新投递接纳，等待已接纳 Handler；期间保持其数据库和发送依赖可用。
3. 取消不再需要新增工作的 Relay，读取运行结果、等待已接纳结算。
4. 排空 Publisher 和失败中转实际发送。
5. 关闭自持有 driver，最后关闭借用连接池和共享事件循环。

这是按依赖设计的示例，具体服务可以调整各类接纳的先后，但必须满足“依赖的使用者退出后再关闭依赖”。容器停止 deadline 还要覆盖前面所有步骤，不能只等于单个 PublishTimeout。

## Python 同进程退出有什么特殊点

PeriodicRelay 运行在宿主已有 asyncio loop 上；await start 显式创建任务，notify 只是加速扫描的提示。wait 暴露扫描异常，宿主需要监督它。已有单进程调度器的 qs-ai 可以复用原结算原语，不必为了接 SDK 再运行第二套 Relay。

stop 先停止接纳并等待当前 attempt。到 shutdown_seconds 后取消任务，再等待任务结束并抛出超时。取消是协作式的：如果 callback 吞掉 CancelledError 并继续运行，等待仍可能超过该预算。这个参数不是强制终止外部调用或事务的保证。

NSQSubscriber.stop 先将 RDY 降到 0，再等待已接纳 tasks；到期后请求取消。若 Handler 不合作，它抛出 TimeoutError 并保留 readers／资源责任，防止关闭正在被原提交使用的资源。宿主不能随后关闭数据库却报告“停止成功”。

Python Publisher.stop 先在 grace_seconds 内等真实 pynsq callback，随后关闭自己持有的 client 并等待 closed_event；此时仍未确认的 PUB 保持 Unknown。它的停止流程包含强制关闭路径，与 Go ManagedPublisher.Close 超时仍保留 driver、另行显式 Interrupt 的合同不同。publish 超时本身仍不能当作发送结束。共享 asyncio/Tornado loop 最后由宿主关闭；SDK 不额外开进程、线程或独立 loop。

## 重启后怎样恢复，怎样不误触业务执行

恢复有三类不同依据：

| 原持久状态 | 合理恢复动作 | 不应做的动作 |
|---|---|---|
| 待发布意图、过期 publishing 租约 | 原 ID／原 wire 再尝试运输，栅栏拒绝旧结算 | 生成新事件 ID、改原正文 |
| 回执型消息已 PUB 但没有认证接受 | 按宿主持久预算继续等待或重投原通知 | 把 PUB OK 当作业务 confirmed |
| 外部模型／通知调用结果未知 | 查原执行事实、冻结配置、回执并进入宿主治理 | 因消息恢复而自动再次调用供应商 |

例如 qs-ai 的任务已经接单，原模型调用结果未知，重启应恢复原任务状态和冻结配置；“重发已经持久提交的结果通知”与“再次请求模型生成结果”是两条不同操作。SDK 只提供运输与结算原语，不授权后者。

Wake、Redis 提示或进程内 channel 丢失时，原数据库扫描仍应继续。没有提示不意味着没有工作；提示送达也不意味着意图已经提交。

## published 原行重排怎样留下审核依据

标准 MySQL `Appender.RequeueConfirmed` 只条件更新原 published 行。它要求原 RecordID、ExpectedVersion、ExpectedFingerprint 和 RequestID；不替宿主查业务效果或检查操作者权限。

一个安全的宿主流程应为：

```text
业务扫描证明原 E1 效果确实缺失
→ 固定原行、原内容指纹和版本
→ 宿主审核／授权恢复
→ 在同一个宿主事务中写授权审计并 RequeueConfirmed
→ Commit
→ Relay 使用原 E1 和原 wire 再发布
```

SDK 保留原身份、正文、计数和此前运输确认，增加 version 并关联审计 RequestID。版本已变化或指纹不符返回 ErrStaleRequeue。RequestID 只是审计关联，不能代替授权；Commit 结果未知时应回查审批账本和原行，不能无条件再次重排。

回执型 `RearmAck/rearm_ack` 的用途更窄：补发 receipt-free final ACK。它保留原 wire 和失败预算；成功的重复 PUB 不消耗该 ACK 的失败预算，Unknown／失败仍消耗。它不能用于重启需要业务回执的命令，更不会解除 held 或创建 ACK 的 ACK。

## 回退时必须保留哪些责任

只验证旧镜像能启动还不够。旧版本需要看懂未结束原行、原 schema、原 wire 和旧密钥；需确认新旧实例能否按同一 schema 和领取栅栏安全并存，禁止绕过栅栏的重复竞争。在实际回退单中逐项说明 pending、publishing、published、held、quarantined 和执行未知状态由谁接管。

队列为空、容器健康、主分支合并都不是删除原责任的依据。正文保留、解密窗口、认证回执和业务恢复授权仍属于宿主治理。SDK 不自动续租、销毁历史正文或管理生产回退。
