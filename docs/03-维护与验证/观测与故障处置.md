# 观测与故障处置

排查可靠消息应先找“原业务事实是否提交、原意图停在哪里、谁仍承担下一步责任”。队列 depth=0、Outbox 未完成数=0、容器 healthy 都不能单独证明下游业务完成。

SDK 提供有限的 Relay 事件和状态快照结构；宿主负责真实数据库读取、指标、业务对账、告警渠道与恢复授权。本篇用具体停点说明怎样读这些证据，不提供直接改生产行或重发业务的命令。

## 先将同一原意图串起来

针对一个原应用事件，采集顺序应为：

```text
宿主部署版本／配置／观察时刻
→ 原业务唯一关联是否已经提交
→ 原Outbox行及指纹／wire摘要
→ 领取token、version、到期和发布结果
→ 各来源nsqd的topic/channel
→ 消费端权威接单／业务事实
→ 原业务回执或最终效果
→ 尚未结束的责任与恢复授权
```

应用消息 ID 与 NSQ 物理 TransportID 分开保存。原 E1 重投可以产生 M1/M2，不能因为物理身份不同就把业务效果相加；相反，业务唯一键也可能是答卷到测评的关联，不一定存在按 E1 保存的 Inbox。

先绑定日志来自哪个实例、Store、producer/destination 和 channel。生产版本无法绑定、某个 Profile 未采集或采集范围不完整时，写 unknown；不要用上一轮成功记录解释今天的现场。

## 状态快照实际包含什么

[outbox.StatusSnapshot](../../outbox/status.go) 是某时刻某 Store 的读取结果。StatusReader 由宿主实现，不是 SDK 构造后自动查询所有数据库。

标准 [BuildStandardStatusSnapshot](../../outbox/status_builder.go) 只接受并输出 pending、retry_wait、publishing、quarantined 四个未完成状态。它拒绝未知／重复状态、负计数以及非空状态缺失最老创建时间；未传入的合法状态补为0，年龄小于0时归零。

下面是合成快照，不能当作生产水位：

```json
{
  "store": "example.mysql",
  "generated_at": "2026-10-06T12:00:00+08:00",
  "buckets": [
    {"status":"pending","count":2,"oldest_created_at":"2026-10-06T11:58:00+08:00","oldest_age_seconds":120},
    {"status":"retry_wait","count":0,"oldest_age_seconds":0},
    {"status":"publishing","count":1,"oldest_created_at":"2026-10-06T11:59:50+08:00","oldest_age_seconds":10},
    {"status":"quarantined","count":0,"oldest_age_seconds":0}
  ]
}
```

这里的120秒是**创建年龄**，不是到期后滞留120秒。一个昨晚创建、今晚才开放的 Task 提醒可以很老，却还未到期；判断扫描停滞还应查 next_attempt_at、lease_until 和业务计划时间。

标准快照不包含 published，也不包含 Broker depth、消费回执或业务完成。所有桶为0只表示读取范围内没有这四类行，不表示 published 消息已产生全部效果。回执型表的 staged／awaiting_receipt／held 应由宿主按独立合同展示，不能硬塞进标准 Builder。

宿主源码实例：[QS MySQL reader](https://github.com/FangcunMount/qs-server/blob/2ccc2de44bbd45e26d29e7e130da518cc32426f0/internal/apiserver/infra/mysql/standardoutbox/status.go)、[QS Mongo reader](https://github.com/FangcunMount/qs-server/blob/2ccc2de44bbd45e26d29e7e130da518cc32426f0/internal/apiserver/infra/mongo/standardoutbox/status.go)、[IAM reader](https://github.com/FangcunMount/iam/blob/c8fc1fe61a32056368148e232e96d32763c15ba5/internal/apiserver/infra/mysql/eventoutbox/standard_status.go)。各自查询与缺字段验证属于宿主责任，SDK Builder 不检查“是否漏读了一个库”。

## 读取错误为什么不能转换成健康的全零

```go
// 宿主片段：reader 已绑定目标Store，采集时间由宿主明确提供。
snapshot, err := reader.OutboxStatusSnapshot(ctx, observedAt)
if err != nil {
    // 标记采集失败／unknown；不覆盖为全零快照。
    return err
}
// 校验Store与范围，展示GeneratedAt和采集错误状态，再消费snapshot。
```

同样，旧快照必须显示其 GeneratedAt 与过期状态。不能把上次零积压无限缓存为当前健康。业务方需要看到“没有积压”和“现在读不到积压”两个不同结果。

QS 的实际 [StatusService](https://github.com/FangcunMount/qs-server/blob/2ccc2de44bbd45e26d29e7e130da518cc32426f0/internal/apiserver/application/eventing/status_service.go) 可以在某 Reader 失败时仍返回整体 HTTP 200：对应 Outbox 带 degraded=true/error，没有成功快照。因此状态码不够，还需逐个核对预期 Store、Profile、degraded/error 和 GeneratedAt。

[StatusReporter](https://github.com/FangcunMount/qs-server/blob/2ccc2de44bbd45e26d29e7e130da518cc32426f0/internal/apiserver/application/eventing/status_reporter.go) 采样失败只增加失败计数，不清空旧 Gauge。上次 backlog=0 可能继续显示，应同时看采样失败和新鲜度，不能从一个零 Gauge 推断当前可读。

## Relay Observer 怎样判断技术进度

[Relay Observer](../../relay/relay.go) 是同步 callback，多个已接纳投递可并发调用。SDK 没有自动注册 Prometheus exporter，宿主映射这些有限事件：

| Event.Kind | 实际触发 | 应如何解释 |
|---|---|---|
| scan_succeeded | 一次真实 ClaimDue 成功，包括空批次 | 扫描依赖可读；不是有消息成功发送 |
| claim_failed | 领取／扫描返回错误，Run退出 | 扫描故障交给宿主监督；不能只看进程还活着 |
| publish_result | 发布得到 Confirmed/Unknown/Rejected | Broker运输结果，与业务接受分开 |
| write_succeeded | 对该结果的条件状态写回成功 | 该次技术结算完成 |
| write_failed | 条件写回返回错误 | 数据库结果可能未知，查原行 |
| stale_write_rejected | 旧claim写回被栅栏拒绝 | 不覆盖新所有者；查实际耗时和当前行 |

Event 没有消息 ID，逐 ID 判断需由宿主原行或受控审计绑定，不能把匿名 Observer 事件直接归给 E1。例如核对同一次发布已 Confirmed、条件写入却失败，仍不能展示“E1 published”：数据库可能已更新，也可能未更新。需要读原行；后者会等待租约回收，前者不再被标准扫描领取。

claim_failed 后应降低对应扫描健康，并保留宿主监督重启计数；只有后续 scan_succeeded 才有新扫描恢复证据。一个正在重启的 goroutine 不等于数据库扫描已恢复。

QS 的 ScanHealthy=true 只表示一次扫描成功，可以是空扫描；PUB Unknown 或写回失败不会自动将它改为false。LastFailureKind 还可保留历史值，非空不一定代表仍在故障。Observer 按 Kind 解读，scan_succeeded 没有真实发布结果，不能把其默认 Outcome=Unknown 计成一次发送未知。

Observer 必须快速、不阻塞、并发安全。慢邮件／HTTP 输出应交给宿主自己的有界系统；SDK不发送邮件、不指定告警接收人。Event.Err 是受控诊断入口，不能未经筛选输出 driver 原错误、原正文或凭据。

## 指标至少分开哪些层

| 层次 | 建议宿主关联的观测 | 误用例子 |
|---|---|---|
| 本地持久意图 | 各Store状态数、创建年龄、到期后滞留、租约 | 把未来计划的创建年龄当发送超时 |
| Relay／发布 | 扫描健康、监督退出、发布结果、写回失败 | 把PUB确认当报告完成 |
| Broker | 每个节点及topic/channel的depth、in-flight、deferred | 只看一个节点，或depth=0就宣布无丢失 |
| 消费／失败中转 | 处理结果、REQ、中转、失败账本提交 | 把原消息FIN当失败审计已提交 |
| 业务回执／效果 | 原任务持久接受、报告、权限权威版本 | 用技术成功替代产品结束点 |
| 生命周期 | handler和真实driver退出结果 | Close到期就报告排空成功 |

逻辑业务预算、Outbox 领取次数、失败次数和 NSQ 物理 attempts 必须分别计数。标准 attempt_count 包含领取，failure_count 仅在成功条件 Retry/Quarantine 时增加；回执型 attempts 对业务通知和 receipt-free final ACK 的规则也不同。

指标标签使用有限的 Store、事件种类、结果分类等维度。原 ID、subject、组织个人信息、正文、密钥和完整 error 不作为高基数公共标签；需要逐 ID 定位时在受控审计系统关联。

Python 当前没有与 Go Observer 对称的统一事件接口，宿主在 loop／callback／事务边界观测。不要为了面板一致虚构不存在的 Python SDK 指标。

## 场景一：pending 变老但 Broker 没积压

先查原行 next_attempt_at 是否到期，再查 Relay 的最后 scan_succeeded、claim_failed 和宿主监督状态。如果还未到计划时间，不应重排；如果扫描已经退出，恢复原扫描和依赖即可。

若扫描成功但行仍没被处理，检查路由、集合／索引、每批限制、并发和发布容量。只增加消费者无助于解决尚未 PUB 的积压。不要复制一个新事件去“测试一下”，那会丢失原责任。

## 场景二：publishing 超期且出现 stale_write_rejected

可能的时间线：

```text
A领取E1／version7
→ A调用耗时超过lease
→ B领取E1／version8并结算
→ A迟到写回，被拒绝
```

读当前原行判断 B 是否已经结算；检查 publish/write timeout、driver真实耗时和数据库时钟。栅栏拒绝是保护动作，不是应该绕过的错误。A/B 仍可能都向 Broker 发布，消费端须按原业务事实幂等。

恢复依靠原租约和原 bytes，不能手工删除 claim_token、重算指纹或把原行计数归零。

## 场景三：awaiting_receipt 一直不结束

沿两条方向分别查：

1. 原通知是否被接收端认证并持久接受；已接受事实与原 ID/BodySHA 是否匹配。
2. 对应回执是否在接收端原事务暂存、发布、返回并在发送端验证结算。

业务已接单但 ACK 丢失，只需要补原通知／原 ACK，不需要重跑业务。正文引用不可读或旧 key 不可用时先恢复原认证与读取责任。不能因为 PUB 成功就强制改 confirmed，更不能用一份当前配置重建旧任务。

## 场景四：原消息已 FIN，但失败账本仍空

原消息的 FIN 可以发生在终端中转 PUB OK 后，失败消息自身尚未提交审计。核对来源 nsqd 的失败 topic/channel、失败 consumer 连接、F1/F2 重复和 FailedHandler 数据库错误。

FailedHandler 持久提交成功才 FIN 失败消息；不可用时应 REQ。中转 PUB确认后的内存消息仍可能在 Broker 强杀后丢失，标准 Outbox 不会从“失败审计为空”自动推断是否要重发原业务。

不要把日志中“handoff confirmed”写成“业务失败账本已提交”。两次 FIN 及对应测试见[投递与消费](../01-核心设计/投递与消费.md)。

## 场景五：Outbox 和队列都空，但业务效果缺失

先查原 published 行、原业务关联、接单回执和真实效果，确认是缺失而非查询范围／权限错误。NSQ PUB OK 后的丢失窗口不能由标准 Relay 自动补齐。

宿主应形成可审阅的原消息恢复计划：原效果缺口、原不可变内容、预期版本、操作者授权、审计请求以及未知副作用核查。满足条件后才使用 RequeueConfirmed 原行重排；SDK 不运行宿主业务效果扫描、不审批、不直接补业务效果。

如果模型调用结果未知，应查原执行事实或进入人工治理，不能把报告暂不可见当作重新调用供应商的证据。

## held、quarantined 与旧预算怎样处理

隔离／hold 表示技术自动路径停止，但原责任没有消失。查错误分类、原身份、认证、大小、历史计数和业务状态，再由宿主授权入口决定处置。

receipt-free final ACK 在旧版可能把成功 PUB 也计入 attempts。新版本不能推断旧计数中哪些是真失败，不自动归零或解除 held。重复消息到达、部署新版本或恢复 Broker 都不自动授予继续发送的预算。

隔离的 mock 数据也应按本轮明确范围处理，而不是将“某批历史是mock”扩展为删除所有 held／历史正文的许可。

## 停机超时和提示失联的边界

Drain/Close/stop 到期后保留对象和未完成责任，核对实际 driver、consumer、timer 和 handler 是否结束。Go 的再次 Close／Interrupt 与 Python stop 的合同不同，按[生命周期](../01-核心设计/生命周期与恢复.md)处理，不用超时返回代替实际退出证明。

Wake／Redis signal 失联时，恢复权威回查或持久扫描。提示不是事实，不能把 Redis Publish 成功记成接单，也不能因提示丢失重新创建业务意图。

## 结案应留下什么证据

处置记录至少绑定精确宿主／SDK版本、采集范围、原安全摘要、状态和版本前后值、真实效果或回执、执行者及授权、时间和停止／恢复结果。业务结束点由宿主定义，源码与测试结果独立记录。

SDK 测试只覆盖其对象合同，生产阈值、值守与邮件渠道仍由宿主运维维护。故障验证使用[测试与故障验证](测试与故障验证.md)的隔离入口；不将排查文档变成未经审核的生产修复脚本。

IAM 的 [readiness](https://github.com/FangcunMount/iam/blob/c8fc1fe61a32056368148e232e96d32763c15ba5/internal/apiserver/container/readiness.go) 是另一个具体宿主政策：它检查标准和历史状态、读取错误与过老积压；兼容 /health 摘要不能代替 /readyz。IAM reader 并未直接使用 SDK 四桶 Builder，不能假设所有宿主具有相同状态名和健康阈值。
