# 观测与故障处置

本文说明SDK提供的技术状态、Observer和故障处置边界。适用于当前Go/Python合同；宿主负责指标、业务对账、权限、告警阈值和人工治理。本文不提供直接修改生产行或自动重发业务的操作命令。

## 先辨认完成点

观测先回答“谁已完成哪一段”。数据库中业务事实已提交、Broker接受、NSQ FIN、接收者持久回执和最终业务效果是不同证据。一个数字为零或容器healthy不能证明整条链结束。

| 观测对象 | 能解释什么 | 不能替代什么 |
| --- | --- | --- |
| `outbox.StatusSnapshot` | 某时刻某Store各状态数量、最老记录年龄 | Broker投递、消费者完成或业务效果 |
| `relay.Event` | 扫描、发布结果和条件写回的技术进度 | 所有失败的业务原因、完整时序指标 |
| NSQ depth / in-flight / deferred | 某节点、topic/channel运输积压 | Outbox未发现行、held/quarantined、已丢失消息或业务回执 |
| 回执型Outbox stage | 待发布、等待宿主回执、技术hold及结算 | 无回执ACK的业务执行确认 |
| 宿主业务/Inbox/回执 | 是否持久接单、去重、完成或结果未知 | 所有Broker节点/所有消费者的可用性 |

状态机定义见[事务与Outbox](../01-核心设计/事务与Outbox.md)及[投递与消费](../01-核心设计/投递与消费.md)，不要把不同表中同名“confirmed”合并为一个成功指标。

## Observer和状态快照合同

Go [Relay Observer](../../relay/relay.go)是同步callback，必须快、非阻塞且并发安全。SDK给出有限种类与结果，宿主映射成自己的计数器和健康状态：

| Event.Kind | 含义 |
| --- | --- |
| `scan_succeeded` | 一次真实Store扫描成功，包含空扫描；可以清除对应扫描失败健康状态 |
| `claim_failed` | 领取/扫描失败，Run返回宿主Supervisor；已领取行仍由租约保护 |
| `publish_result` | 传输 `Confirmed`、`Unknown` 或 `Rejected`，不等于业务完成 |
| `write_succeeded` | 发布结果对应的条件状态写回成功 |
| `write_failed` | 状态写回失败，不能把此前PUB成功当作持久结算成功 |
| `stale_write_rejected` | 旧claim的迟到结果被拒绝，应检查租约/版本与实际运行耗时 |

`Event.Err`仅供受控诊断，不应原样进入公开日志、Metric label或失败信封。指标使用有限标签；应用message_id、正文、subject、密钥和数据库错误细节不能作为高基数公共label。

[StatusReader](../../outbox/status.go)由宿主实现，它只读取宿主业务数据库，不启动Relay或转移所有权。`GeneratedAt`、Store范围、状态数量、最老时间应一同展示；全零但读取失败、快照过旧或漏掉一个Profile不能表示健康。SDK不设置统一业务时限或发送告警邮件。

Python的Relay、`deliver_durable`、NSQ callback和回执型adapter没有与Go Observer完全对称的统一指标接口。宿主应在callback/事务/loop边界保留安全错误码、状态与时刻，不能在文档中虚构跨语言统一监控面。

## 最小宿主观测面

每个宿主至少关联：业务提交/回执，按Store与状态的未完成数量和最老年龄，发布结果与写回失败，扫描/Supervisor存活，消费重排与失败中转，隔离/held，以及资源停止是否完成。阈值按业务负载、轮询、租约、处理耗时和恢复预算制定。

逻辑重试、领取次数、Outbox发送失败与NSQ物理attempt分别计数。标准Store的 `attempt_count` 包含领取；`failure_count`只在成功条件Retry/Quarantine时增长。回执型 `attempts` 对requires-receipt记录计不确认的投递，对receipt-free final ACK计失败/未知PUB；不能把这几类计数相加得出一个“总重试次数”。

## 通用排查顺序

1. 固定宿主部署SHA、SDK/驱动版本、实际配置和采集时间。先核对日志/状态来自哪个实例、Store、producer、destination和channel。
2. 查原业务事务是否提交，原Outbox/Inbox/回执是否存在及身份/指纹是否一致。未提交事实不能靠补一条消息替代。
3. 查持久状态、到期时间、租约、token/version和条件写回；再查Broker对应节点与channel。避免先重发再询问原效果。
4. 读取消费者的权威幂等/回执与效果。PUB OK、FIN或技术日志不够；不可逆调用未知时保留原记录供宿主核实。
5. 确认谁持有下一步责任：活动Relay、租约恢复、等待回执、终态handoff、held/quarantined还是人工审批。
6. 确认条件后通过宿主授权入口处置，保留原ID、原字节、预算、审批与预期版本。对账完成后再关闭事件，不以清队列作为结案。

## 常见停点与处置边界

| 现象 | 首先核对 | 允许的恢复边界 |
| --- | --- | --- |
| pending / retry_wait变老 | due时间、扫描存活、路由、DB/Broker、容量 | 恢复原Relay/依赖后扫描原行；不复制新消息 |
| publishing租约逾期 | 原调用是否仍在途、数据库时钟、当前claim | 租约回收可再投同一原行；消费者需幂等，不覆盖新claim |
| PUB Unknown / 写回失败 | 原wire、Broker接受可能性、持久状态 | 保留不确定性；按宿主技术策略重投原身份，不授予业务重试 |
| awaiting_receipt持续 | 已接单回执、返回路径、验证身份、保留正文 | 重投原通知/回查回执；不能把Broker确认强制改成业务确认 |
| quarantined / held | 技术预算、认证/大小错误、历史计数、原效果 | 人工核对和宿主审计；重复消息不得自动撤销hold或刷新预算 |
| 失败中转积压 | 源节点failure channel、确认丢失、持久录入事务 | callback持久录入后才FIN；允许重复中转但录入需幂等 |
| 旧final ACK已held | 原计数是否含成功PUB、技术错误、原回执 | a2不自动清算历史；由宿主有审计的处置决定 |
| Drain/Close超时 | 实际driver调用、consumer/timer/goroutine是否退出 | 保留未完成所有权并重核Close；超时返回不是安全停止完成 |
| Signal断开或丢失 | 发布/订阅来源、TTL与主动回查 | 回查权威事实/持久扫描；不把提示升级为隐式可靠队列 |

NSQ内存消息在PUB确认后强杀Broker仍可能丢失。标准Outbox的published行不会因此自动重新pending；必要效果须宿主对账，选择原行审计重排或回执型合同，见[NSQ故障边界ADR](../04-设计决策/003-复用NSQ与故障边界.md)。

## 操作责任与验证

SDK只提供条件写、状态读取、明确生命周期和技术接口。组织范围、业务效果验证、谁能审批、恢复时限、通知收件渠道和具体回退镜像属于宿主。SDK不运行工作流、不重试未知模型调用、不重建冻结配置，也不创建运维定时任务。

故障验证使用[测试与故障验证](./测试与故障验证.md)列出的隔离入口。现场记录至少保存原身份与安全摘要、状态/版本前后值、权限/审批、时间和实际执行者；敏感正文与密钥留在宿主受控系统，不复制进公共文档或失败信封。
