# 兼容与升级

升级可靠消息 SDK，最重要的是交接未结束原消息的责任。“旧版能读一条 pending 行”不能证明它理解新失败预算、历史密文、业务回执或人工恢复状态；“新镜像能启动”也不能证明旧镜像安全回退。

一次升级要分别比较 API、wire、持久状态、驱动和宿主装配。Go/Python 独立版本、三种 Outbox 合同分别演进；包版本不是业务 schema 版本。已发布 tag、源码与资产见[发布索引](../releases/README.md)。

## 先确定升级的究竟是哪一层

| 层 | 应比较的对象 | 常见错误判断 |
|---|---|---|
| 公共调用 | 类型、错误、Start/Run/Close及资源所有权 | 编译成功就认为生命周期不变 |
| 原消息协议 | ID、fingerprint、wire revision、protected Context | 新包版本自动升级所有原消息 |
| 持久结构 | 表列、索引、状态、计数、条件更新 | CREATE IF NOT EXISTS能升级旧表 |
| 驱动和服务器 | 原事务检查、时间、确认与关闭行为 | 版本区间内每个补丁均已经测试 |
| 宿主合同 | 业务幂等、准入、冻结配置、回执和恢复权限 | SDK通过测试即可替宿主批准回退 |

本次文档重写没有改变库实现、schema、依赖或锁文件，不需要因此给 IAM/QS/qs-ai 执行 DDL 或部署。当前主线机制与已发布 Go mq-ai.2／Python a2 的差别应按真实 diff 核对，不能将文档变深解释为新 SDK 运行功能。

## 一个真实升级：旧表缺新增失败诊断列

Go v0.1.0 标准 MySQL 表没有 failure_count 和 updated_at。v0.2.1 新 Store 要使用它们，New 仍可成功，因为构造不访问数据库；第一次 ClaimDue 才会暴露缺列。

```text
只升级包，未迁移旧表
→ Store.New成功
→ 宿主Run开始
→ ClaimDue访问缺失列而失败
→ Run退出，意图仍未发送
```

宿主应先安装加法迁移，再启动需要这些列的新执行者。当前固定版本隔离脚本采用：

```sql
-- 仅说明旧v0.1.0隔离表的迁移，不是可直接套用的生产操作单。
ALTER TABLE rm_outbox
  ADD COLUMN failure_count BIGINT UNSIGNED NOT NULL DEFAULT 0 AFTER attempt_count,
  ADD COLUMN updated_at DATETIME(6) NOT NULL DEFAULT (UTC_TIMESTAMP(6)) AFTER created_at;
```

新建表使用 [schema.sql](../../storage/mysql/schema.sql)，已有表先核对实际结构。重复执行 CREATE TABLE IF NOT EXISTS 不会补这两列，也不能证明原行语义已迁移。

failure_count=0 仅是新列起点，不能从旧 attempt_count 推算历史失败：attempt_count 包含领取、租约恢复等动作。升级保留原 ID、payload、fingerprint、发生时间和原计数，不重新生成历史消息。

## 双版本试验证明了什么，没有证明什么

当前 [integration.sh](../../scripts/integration.sh) 真正编译固定发布版本：

```text
v0.1.0 → 1cab5531ee985fff9561b94c9b3d396230f870d4
v0.2.1 → 5bbbacb15f9c044e7ef27d4384110a97b92c745f
```

这些不是当前 Appender 配旧表的替身。探针覆盖两个版本的普通 pending、双向活动租约等待与到期回收、旧 token/version 栅栏、双库并行 claim、并行 Relay 和 PUB 确认丢失交接。

但它也刻意保留两类降级缺口：

| 缺口 | 实际反证 | 维护含义 |
|---|---|---|
| 旧 Store 不维护新 failure_count | 三次 Retry 加一次 Quarantine 后，新计数只有2 | 旧版仍能发，不等于失败预算可安全交接 |
| 旧 Mongo 文档缺 created_at | 旧文档可投递，但部分文档依旧没有诊断时间 | 状态页／年龄完整性需另验证，不能补造时间 |

这类预期缺口被成功复现，测试仍可以通过。不能将其写成“所有状态可无条件降级”，更不能外推为 IAM/QS/qs-ai 的全部新标签、部署镜像和业务恢复都已兼容。

旧新标准 Store 支持通过同一领取栅栏竞争；是否允许不同版本并存，还取决于 schema、计数、wire 和宿主策略。禁止的是绕过兼容判断和栅栏的重复执行，而不是笼统禁止所有多实例发送。

## 后续两个演进为什么不能当成同一种迁移

### 原 published 行审计重排

Go m6.2 加入 [RequeueConfirmed](../../storage/mysql/requeue.go) 和可选 manual_replay_request_id/manual_replay_version。普通 Append/Claim/Confirm/Retry 不依赖这两列；使用原行重排时必须安装并核对它们。

宿主先证明原业务效果缺失、核验原内容和版本、批准恢复，并在同一事务写审批审计。SDK 条件改变原 published 行，保留原指纹、计数与运输确认，不直接 PUB、不授予模型重试权限。

缺审计列是 schema 错误，不应跳过审计继续更新。操作结果未知时回查原审计和行状态，不能无条件重复。

### 回执型表与 final ACK 预算

Go mq-ai.1／Python 0.2.0a1 增加独立[回执型 schema](../../delivery/mysql/schema.sql)。它不是把 Go rm_outbox 或 Python 原 pending/delivered 表换个名字；确认点、顺序和持久状态不同。

mq-ai.2／0.2.0a2 没有 DDL 变化，修正 receipt-free final ACK：

- 成功 receipt-free Published 不增加 attempts；Retry 结算增加 attempts，Hold 本身不增加。宿主对 Rejected 直接 hold 时，不应将其也算成一次 Retry。
- 重复事件补发 ACK 保留原失败计数。
- 已 held 不因重复事件自动解除。

旧 attempts 可能混有成功 PUB，补丁无法判断其中哪些是真失败，不自动归零或解除 held。降回 a1 会再次出现旧预算／hold 行为，不能因 schema 相同就称回退无风险。

业务通知 requires_receipt=true 仍需认证原业务回执；final ACK 是 receipt-free，无 ACK 的 ACK。混用确认终点会比版本 API 不兼容更危险。

## 原 wire 和安全密钥怎样交接

网络 Revision1/Revision2、业务 schema、protected profile 和包版本独立。升级不能把已持久的原消息重新编码为当前正文、重算发生时间或重新 Seal。

旧 key 与原 Body 的保留覆盖待投、待回执、held 和审核的回退窗口。新版本能解析一条新密文，不能证明旧版本能读所有历史 key/header；按原消息族验证旧读者、实际路由和认证 Context。完整机制见[消息身份与协议](../01-核心设计/消息身份与协议.md)及[安全与大消息](../01-核心设计/安全与大消息.md)。

跨语言共表测试使用本轮源码 Go helper 发布、Python重新扫描与结算，证明指定源码合同互通，不是两份独立发布二进制的版本交接。Go标准 leased Store 与 Python原表接口仍不对等。

## 时间升级为什么不能批量加减八小时

标准 MySQL DATETIME 保存显式 UTC 时钟数字，Mongo 保存绝对时刻；业务与运维显示 UTC+8。调度列没有偏移信息，连接 loc 和 session时区改变不应重新解释原数字。

早期 m2.1→v0.1.0 的修复将传 time.Time 改为显式 UTC 字符串，避免 driver 二次转换，未修改历史值。当前[时区测试](../../tests/integration/mysql_timezone_test.go)覆盖 loc0／8、session+00／+08、参数插值开关共8组。

历史记录若来自不同写入规则，先确认原来源，再由宿主制定迁移。不能因“统一UTC+8”批量平移历史调度列或改 occurred_at，这会改变原身份指纹和执行时间。

## 一次宿主升级怎样变成可审阅结果

以“版本＋原行责任”形成升级单，而不是只有部署命令：

1. 固定目标tag／源码／制品摘要，排除非预期 replace、本地源码覆盖。
2. 列出当前 schema／索引、原未完成状态、原 wire/key、未知副作用与执行者。
3. 安装所需加法迁移，先验证读取、追加、领取和结算，再开放新写入者。
4. 运行对应真实资源验证和宿主幂等／回执／停止路径，不用替身代签业务。
5. 明确旧新是否安全并存、谁接管过期租约、哪些状态必须先排空。
6. 回退逐状态检查原行、计数、正文、密钥和宿主恢复能力，保留所有未结束责任。
7. 切换后按原业务关联／原ID对账，将代码、CI、部署与业务效果分别记录。

历史 mock 可以经宿主明确授权归档，不能据此跳过未结束真实任务或未知调用核验。升级结束必须能说明“哪些原责任已结束，哪些仍有归属”。

## 版本承诺何时可以扩大

当前 Go 0.x 和 Python alpha 各自固定版本，不能因预发布成功就声称建立了 v1 稳定承诺。计划中的稳定合同需要明确 API、身份、持久状态、弃用替代与迁移窗口。

新增数据库、驱动、Broker、动态拓扑或 Python 多进程前，先补其原事务、确认丢失、迟到执行者、重启和退出证据，再扩大支持范围。机制取舍见[独立语言版本 ADR](../04-设计决策/004-语言与包独立版本.md)；版本级已执行结果仍以对应发布记录为准。
